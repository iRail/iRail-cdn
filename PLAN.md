# Plan: an iRail CDN provider built on Linked Connections v2-alpha

## Scope and specification

The production timetable will follow **[Linked Connections v2-alpha](https://linkedconnections.org/specification/2-0-alpha)** (see PR opening in ../lc-website) as its interoperable routing core, with a separately versioned **iRail extension profile** for the rest of the provider. The baseline is the draft and converter implementation checked on 8 November 2026: JSON-LD discovery, Arrow connections/stops/trips/routes/transfers, IRI-based identity and RFC 6570 feed templates, region-aware paging with immutable Arrow URLs, linked trips, and the explicit limit on frequency-based real-time matching. The LC draft is evolving; pin its specification, context, vocabulary and schema artifacts by reviewed commit or content hash before implementing a release.

**All iRail features in this plan remain required.** The public LC core defines what an independent routing client can consume. iRail consumer applications additionally need complete stop-visit views, backed by this provider's connections, richer identifiers and station metadata, RIV reconciliation, normalized real-time state, crowdedness/forecasts, rolling stock, geometry, alerts/status, history, and the twelve-hour update feed. Keeping those as extensions does not make them optional for iRail API parity.

The current [specs/](specs/README.md), executable schemas, synthetic IPC fixtures and example reader now use the **LC2-alpha core** with `manifest.jsonld` and `connections`, plus separately versioned iRail side tables. The schema/context baseline is pinned in [config/lc-contract.json](config/lc-contract.json). There is no deployed older format or compatibility period to maintain. Production GTFS conversion/publication and live normalization remain to implement; a conforming synthetic fixture does not establish complete source coverage or native Pages HTTP behavior.

The `gtfs2lc` **`feat-arrow` working tree now implements the current LC core**; the remaining timetable work here is integration, validation and publication, not another GTFS converter. [Converter readiness](#converter-readiness-8-november-2026) records the verified implementation and its source-pinning qualification.

**Hosting split:** GitHub Actions runs gtfs2lc and builds all planned datasets; GitHub Pages publishes those static releases directly. Cloudflare Workers, R2 and Durable Objects handle live collection, real-time snapshots and the update feed. Planned conversion and planned-file delivery have no Cloudflare dependency. Production planned hosting remains to implement. The current optional Worker adapter can serve the same fixtures from local R2.

**Implementation order:** finish the standalone Node build, GitHub Actions workflow and Pages publication first. Extend and deploy the Cloudflare live service afterward. Planned publication must be usable before the live adapters, normalized overlays or feed integration are complete; all of those remain required in the later phase.

The provider should supply enough data for an independent browser or server to plan journeys, show station boards, inspect dated trains and compositions, render routes, and display disruptions and crowdedness. The iRail API can become a compatibility layer over those datasets. Application-owned feedback, logs and website assets remain separate.

1. **Planning:** adjacent scheduled call-to-call connections, service dates, original sequences and canonical IRIs, generated from one GTFS archive plus deterministic identifier/partition configuration. Publish the LC `connections` dataset as independently readable pages; use the implemented LC schema and discovery shape. Crowdedness observations and forecasts are published independently in occupancy.arrow.
2. **RIV and GTFS-RT:** retain original trip-updates.pb and materialize effective state in delays-cancellations.arrow. RIV delays may be newer. Resolve each matched entity/field/scope using source times, expiry and provenance.
3. **Compositions:** ordered rolling-stock units per dated run and segment, including confirmation, capacities, nullable amenities and observation time.
4. **Shapes:** a polyline index with downloadable ordered point files. Route display geometry is distinct from a physical railway graph; detailed tracks need a separate source and contract.
5. **Supporting data:** stops, trips, routes, transfers, occupancy, alerts, associations and stop status. Timetable publication uses connections, with no calls dataset or call-view service. API/planner consumers reconstruct ordinary stop visits, including terminal arrivals and intermediate dwell, from connection endpoints. Keep stable stop-event identities for independent overlays without building a second timetable representation.
6. **Global IRIs:** operator namespaces such as be.sncb are shared by that operator's collection channels. Configure identity/named bases, per-entity templates, safe field/date resolvers and source overrides. Preserve established SNCB station IRIs, check collisions and pin effective rules with each release. Numeric indices accelerate scans within one release.
7. **Twelve-hour LDES 2.0 feed:** normalized producers submit changed source states to a shared durable journal. Publish a description message and one RDF Message per member, with LDES interval relations, Zstandard-compressed Jelly-RDF 1.2, the same entity IRIs, and 12-hour commit-time retention.

The specification and implementation status are separate. The scaffold includes synthetic Arrow data, original GTFS-RT collection, authenticated RIV transport, a field resolver and a generic durable LDES. Production timetable conversion, endpoint-specific RIV parsers/jobs and normalized producer wiring remain to implement. An empty unavailable table is not evidence of a successful empty source response.

## LC routing core and iRail extensions

An ordinary LC client must be able to read the timetable without knowing the iRail profile, loading a separate calls table, calling RIV, or parsing Jelly-RDF. An iRail client starts from the same pinned release and discovers the additional datasets. Both views share core dictionary rows and canonical entity IRIs. Raw GTFS IDs remain available to iRail through its source registry and extension data; the LC core no longer requires raw-ID columns.

| LC v2-alpha contract | Planned iRail implementation and migration |
| --- | --- |
| `manifest.jsonld`: `Timetable`, `schemaVersion: "2-alpha"`, `releaseId`, agency `timeZone`; recommended license/rights and coverage | Serve the converter's LC JSON-LD entry point and immutable release manifest as `application/ld+json`, with the implemented IRI-string reference shape. The four reference-table properties are IRI strings, not file-descriptor objects. iRail adds source attribution, legal metadata, coverage, capabilities, identity strategy and extension discovery through its profile. |
| `connections`: a `ConnectionCollection` with `pages`, or a declared template strategy | Consume the converter's explicit `pages` list with page `@id`, bounds, epoch, region and arrival regions. Static GitHub Pages delivery supports forward/backward scans without another search service. Hashes, byte lengths and row counts belong to the iRail integrity catalog, not the minimal LC page contract. |
| Arrow dataset `connections`, with the eleven LC columns in their defined order | Use the implemented LC fields/types/nullability and `schemaVersion=2-alpha`, `dataset=connections`, `releaseId`, `epochSeconds` and region metadata. Keep global connection identity unchanged. |
| `stops`: name/coordinates, parent, transfer buffer, `iri`, nullable `regionIri` | Preserve actual platforms, acyclic parents and canonical station mappings. Map internal numeric region IDs to persistent region IRIs; region membership is fixed within a release. Preserve raw `stopId` as a nullable iRail column or alias mapping, alongside rich station codes, multilingual names, transfer provenance and accessibility. |
| `trips` and `routes`: route index, display fields, mode and `iri` | Use the exact LC column order, without mandatory `tripId`/`routeId`. Retain those raw IDs verbatim as nullable iRail fields or aliases for source reconciliation. Shape references, block/product labels, agency identity and accessibility remain extension data. |
| `transfers`: nullable stop indices, selector fields and types 0–5 | The implemented stop-index schema is nullable. Types 0–3 need both stops; types 4/5 need both trips and may omit stops. Implement GTFS specificity and station/platform applicability. Type 4 permits staying aboard; type 5 requires alighting and regular transfer checks. |
| Optional `realtime[]` links with `tripTemplate`, and `stopTemplate`/`routeTemplate` when their fields are used | For supported scheduled trips, expand the feed's RFC 6570 templates from protobuf IDs and match exact IRI strings to the core dictionaries. Advertise a native LC feed link only when those templates reproduce the release's IRIs. Keep richer lookup-based reconciliation, original protobuf, source/fetch times and independent discovery in the iRail profile. |
| Nullable appended columns or separately discovered resources | Give the iRail profile its own version and JSON-LD terms. Append only nullable fields allowed by LC, or put richer records in separate tables. Validate required iRail values at profile level; do not append old non-null columns and label the result a compatible LC extension. |

The eleven core connection columns are `departureStopIdx`, `arrivalStopIdx`, `departureTimeOffset`, `arrivalTimeOffset`, `tripIdx`, `pickupType`, `dropOffType`, `serviceDate`, `stopSequence`, `arrivalStopSequence`, `iri`. The LC schema reference is the authority for all five core tables. Core files retain the LC schema version; independently specified extension tables carry the iRail profile/version. Do not overload LC's `schemaVersion` with the iRail version or redefine protected LC context terms.

### Identifiers and GTFS Realtime matching

LC permits either release-scoped or stable entity IRIs. The **iRail profile chooses stable canonical IRIs** across timetable releases, preserving existing station authorities and shared RIV/GTFS-RT/LDES identities. That is a stronger iRail identity guarantee, not an additional LC requirement. A delivery release or row number never becomes part of an existing iRail entity's identity merely because the core permits other publishers to scope IRIs by release.

The LC baseline contains no `stopId`, `tripId` or `routeId` columns. Preserve these source identifiers and their source-generation scope in the iRail registry, with nullable appended columns or an explicitly versioned alias side table when consumers need them. Retain the raw-to-canonical mapping across renumbering or ID reuse. Dictionary row numbers still belong to one pinned static release; matching IRIs alone does not authorize joining integer indices across releases.

For a feed advertised in LC `realtime[]`, provide RFC 6570 `tripTemplate` using `trip_id`, `stopTemplate` when `stop_id` is used, and `routeTemplate` when `route_id` is used. Expand from the protobuf field values and match the resulting IRI exactly, case-sensitively, against the corresponding `iri` column. Percent-encode once according to RFC 6570; do not decode/re-encode or otherwise normalize the resulting strings. Verify each supported source-ID-to-IRI pairing during release validation, including IDs containing slashes, literal percent escapes and Unicode.

The existing iRail identity registry supports source overrides, safe resolvers and persistent mappings that cannot always be expressed by those three templates. **Keep that capability.** Do not serialize its resolver expressions as if they were RFC 6570, or invent a template that yields different entity IRIs. When a source requires lookup-based reconciliation, retain its original feed in iRail discovery and normalize it through the iRail resolver/overlays; omit the incompatible native LC feed link. An ordinary LC client can still consume the scheduled core. iRail continues to support that source through its extension profile, with the same canonical IRIs and unchanged archived protobuf.

For fixed scheduled trips, match `start_date` to the service date when present. When absent, use absolute event times and the declared signed-delay window to select a unique candidate, including future runs; reject ambiguous matches. Follow the LC limitation for delay-only updates without a date, rather than guessing from the current clock. Preserve missing predictions and `NO_DATA` as unknown prediction status, with scheduled fallback explicitly distinguished from an observed on-time event.

Frequency-based service remains an iRail extension work item. The LC draft does not define its real-time matching, including `exact_times=1`: expanded instances need distinct trip rows/IRIs, and the original frequency `trip_id` expanded by `tripTemplate` must not match any instance. Never apply one update to an arbitrary expanded row. For iRail support, first specify a generation-scoped alias mapping from `(trip_id, start_date, start_time)` to the expanded trip/run identity and resolve it through the iRail real-time adapter. Keep original IDs and protobuf; until that extension is implemented, declare unsupported coverage explicitly. Frequency instances and additional/replacement services remain on the roadmap rather than being silently dropped with the smaller LC scope.

### Connection publication and consumer responsibilities

This repository publishes LC **connections and reference tables**, plus the independent iRail real-time/enrichment datasets and update feed. It does not build or publish a calls dataset, serve a derived calls API, or maintain a stop-visit projection/index. Do not add `src/timetable/visits.ts` here.

API and planner projects reconstruct stop visits when needed: an incoming connection supplies arrival time/drop-off, an outgoing connection supplies departure time/pickup, and `(tripIdx, serviceDate, stopSequence)` identifies their shared event within one release. That consumer work includes dwell, terminal arrivals, repeated stops and arrival-board page selection. It is not a second conversion job in this provider.

Real-time, occupancy and composition overlays still need to identify runs and stop events by their canonical identities or the connection endpoint keys. Referencing such an event does not require constructing or storing a calls table. Preserve source-supported additional information in the existing independently specified overlays; do not introduce a separate static calls format for it. Call-IRI terminology in the identity/overlay contracts describes those event references.

The executable schemas and generated fixtures publish connections once, without a calls table or calls-file dependency. Preserve that boundary when integrating the production converter.

| Retained iRail resource | Purpose beyond the LC core |
| --- | --- |
| Station/trip enrichment fields or side tables | Existing station authorities/codes, localized labels, transfer provenance, product/mode filters, accessibility and links to shapes or physical units. |
| `shapes.arrow`, `shapes/*.arrow` | Ordered display geometry and call/shape anchors; detailed physical tracks still need their own source and schema. |
| `compositions.arrow` | Ordered units per dated run/segment, confirmation, physical identities, capacities, nullable facilities and observed or explicitly historical formations. |
| `occupancy.arrow` | Independently published official/user observations and forecasts, with call identity, source, model generation/observation time and expiry. |
| `alerts.arrow`, `alert-entities.arrow` | Multilingual disruptions, journey messages and explicit entity associations with validity and provenance. |
| `stop-status.arrow`, `delays-cancellations.arrow` | Resolved RIV/GTFS-RT estimates, cancellation scope, independent arrival/departure platform/status and notes. |
| `identity-strategy.json`, `/feed` and future history views | Release-pinned shared identity rules, twelve-hour Jelly-RDF observation synchronization, and separately specified history/effective-state views. |

Extension discovery must describe station/trip enrichment, shapes, compositions, occupancy, alerts/associations, stop status and normalized real-time snapshots, plus the identity-strategy descriptor and `/feed`. A namespaced link in the LC manifest points to the release-pinned iRail extension manifest; overlay manifests identify their own generations and the static release used by numeric references. Core and extension tables must use identical dictionary indices where they reference the same core dictionaries. Additional live trips, connections and stop-event updates need their own complete contract and mapping; they cannot invent rows in a pinned static dictionary.

### iRail publication policy within LC

- Keep six-hour UTC departure buckets and a target maximum of 50,000 rows per connection page as **iRail implementation choices**, not public LC requirements. A bucket may have multiple independently readable pages. Use the LC page-list strategy initially; do not declare `ScheduledPagination`, whose contract requires one file for each slot/region, including quiet slots.
- Keep the converter's LC reference-table IRI strings and page-list shape intact. Publish a release-pinned iRail integrity catalog with every core/extension data file's IRI, SHA-256, byte length and row count; retain page bounds/epochs/region relationships for validation. The catalog is discovered through namespaced extension metadata, rather than restoring old descriptor objects or undefined bare terms to the LC manifest. Compute hashes after all data bytes are final; do not require a catalog or file to contain its own hash.
- Every final Arrow file URL and immutable release-manifest URL identifies fixed bytes. A scheduled template, if added, must include the release or another content-version component. LC permits mutable redirect lookup endpoints with short caching; iRail initially uses the page list and prefers release-bound lookups if needed later. If a lookup returns another release, discard the mismatched page and restart the query with a newly pinned manifest/dictionaries, without mixing earlier page cursors or overlays. Define boundary/empty-page behavior and keep list/template views consistent.
- Build the core connections, reference tables and shapes/transfers from one pinned GTFS archive and deterministic configuration. Stop-visit reconstruction happens in consumer projects. Curated enrichment, occupancy, forecasts, RIV access or a model failure must not block the timetable. Importing source-backed optional fields never requires a live data collector.
- Normalize raw GTFS-RT identifiers only against a verified source generation. Native LC links must pass the exact template-to-IRI checks; richer source aliases are resolved by the iRail adapter. An immutable old manifest must not silently apply a newer, renumbered source's feed. Use generation-specific live feed URLs or explicitly reconciled iRail views; retain a dated last snapshot when a generation stops updating and expose its stale status. Dynamic feeds and redirects use short caching, not immutable release caching.
- Preserve scheduled run/link identity when applying estimates. Resolve linked runs from the complete scheduled run boundaries, including midnight/DST and next service dates; only type 4 enables in-seat continuation. Evaluate effective feasibility without relinking to an unrelated later run. Explicitly validate timing/stop consistency between adjacent connections of each run.
- For real-time queries, join each endpoint to its own stop event, honor run/stop cancellation scope, and re-sort by effective departure time. Support signed early/late deviations with a documented fetch window. Match future as well as current updates; reject ambiguous run matches. `NO_DATA` ends applicable prediction propagation and retains unknown prediction status; scheduled fallback is not evidence of a measured zero delay.

The updated LC draft distinguishes immutable Arrow files from mutable discovery, separates type-4/type-5 continuation, permits future-run matching and explicitly excludes frequency-based real-time matching. Use those clarified contracts as the baseline. iRail's integrity catalog, stable canonical identity, lookup-based source reconciliation and broader service support are profile choices beyond that baseline. Re-run core conformance checks against the pinned draft before a production cutover.

## Source access and collection budgets

RIV uses https://mobile-riv.api.belgianrail.be and an application key in the x-api-key header. The gateway reads secret RIV_API_KEY; RIV_ENABLED, RIV_BASE_URL and RIV_LIMIT_RPM are configurable, with a default shared budget of 40 requests/minute. [RIV collection](specs/riv.md) specifies all request families and parameters, delay fields, reference discovery, midnight/partial-cancellation handling, functional errors and refresh priorities.

Discover dated runs/board targets from the schedule, deduplicate queries and refresh by expected change and measured coverage. Forty calls/minute cannot refresh every station, both board directions and all train details every minute. Keep protected raw responses private; published normalized fields retain appropriate source attribution and publication rights.

[SNCB's public-data page](https://www.belgiantrain.be/en/3rd-party-services/mobility-service-providers/public-data) points to Belgian Mobility; its [knowledge base](https://data.belgianmobility.io/en/knowledge-base.html) describes static and real-time feed access. Choose a matched static/RT source pair and put source version, attribution, license and freshness in manifests. RIV, curated references, user reports and track data retain separate provenance. A GTFS mirror credential is separate from the RIV key.

## Architecture and publication

GitHub Actions runs the Node batch timetable pipeline with the pinned gtfs2lc implementation. GitHub Pages serves all planned output directly. Workers run the smaller, frequent collection and real-time publication jobs; they do not execute gtfs2lc or proxy planned downloads.

- **Planned builder and delivery:** fetch one GTFS archive, constrain the horizon, invoke gtfs2lc, add static iRail enrichment, validate, and assemble a complete GitHub Pages artifact. It contains LC connections, stops/trips/routes/transfers, shapes and planned reference enrichment, raw-ID aliases, the identity-policy snapshot, integrity catalogs and release-pinned manifests. Reuse core dictionary/IRI assignment; the timetable build needs no live occupancy or RIV input. Include retained immutable releases and latest discovery in the same site snapshot, then deploy through GitHub Actions.
- **Collectors:** minute cron initially mirrors protobuf. Persistent jobs will drive RIV DACS, discovery/detail, composition/occupancy/messages and RSS. The shared gateway already handles bounded transport, authentication, caching and a cross-job budget; normalization, generation checkpoints and outboxes remain.
- **Journal/resolver owner:** ChangeJournal compares source states, deduplicates deliveries, orders commits and retains Jelly-RDF observations. resolveField implements timestamp selection and an explicit fresh-RIV preference. Production materializers and complete effective-state views derive from committed state.
- **Live delivery:** Workers/R2 serve raw protobuf and normalized real-time/occupancy/composition/alert snapshots; `/feed` uses the durable journal. Later deployments use private bindings to the same owners. More Workers do not multiply the credential's upstream budget. Collectors may fetch/cache bounded release dictionaries or alias lookups from Pages for matching, without serving the planned files themselves.
- **Independent generations:** planned data builds daily/on source or configuration change; real-time around 30–60s where budgets permit; other overlays on measured cadences. Indexed overlays declare their static release and link explicitly to its Pages manifest. Planned batch snapshots belong on Pages; frequently revised operational observations remain live even when an upstream field calls them a planned formation or a forecast. All existing enrichment features remain required.
- **API/website:** consume these datasets, plan locally, serialize compatibility fields and use separate write services for feedback/logging.

Configure distinct `STATIC_BASE_URL` and `REALTIME_BASE_URL` values in the integration stage. Pages discovery links to live manifests/feed by absolute URL; live discovery identifies the pinned static release. Both origins support browser consumers. Keep canonical entity IRIs and their identity authority independent of either delivery host. A GitHub Pages project path, custom domain or later delivery-host change must not rename entities.
