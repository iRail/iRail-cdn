# Real-time updates

## Canonical `trip-updates.pb`

Keep the upstream GTFS-RT `FeedMessage` unchanged. MIME is `application/x-protobuf`; discovery includes source/fetch timestamps and a content hash. This preserves entity IDs, unknown protobuf fields in the stored bytes, trip descriptors, cancellations, uncertainty, stop assignments, extensions and future feed evolution without committing to a lossy delay-only schema.

Canonical here means the original **GTFS-RT representation**. Effective iRail real-time state also uses [RIV delays and detail](riv.md), which can be newer. Preserve both provenance channels, resolve fields explicitly, and use the same [canonical IRIs](identifiers.md) across both sources and the LDES.

The initial scheduled collector only accepts a `FULL_DATASET` snapshot (the GTFS-RT default when incrementality is omitted). It rejects differential feeds until a stateful reducer exists. It also requires a positive feed timestamp, bounds response size, rejects a snapshot older than the current discovery record when checked, and only publishes after successful storage. Publication still needs serialization to exclude overlapping poll races. It does not claim to validate every GTFS-RT semantic constraint. Empty full snapshots are valid and must replace previous entities rather than retain old cancellations indefinitely.

No URL is configured by default. Test fixtures use mocked fetches and require no key. Polling in this scaffold is once per minute; a deployment can target 30-second collection with a suitable scheduler and source budget. An old successful snapshot remains downloadable after upstream failure; freshness must be evaluated from `feedTimestamp` and `fetchedAt`, not its HTTP cache age. An operational policy should declare the stale threshold (initial candidate: 120 seconds) and make stale state visible rather than assume zero delay.

## Applying a snapshot

Follow the [GTFS-RT semantics](https://gtfs.org/documentation/realtime/reference/) and [trip-update rules](https://gtfs.org/documentation/realtime/trip-updates/), using raw GTFS `tripId`, service date and, where required, trip start time. ID namespaces from unmatched static/RT feeds cannot be joined by public train number alone. Resolve `stop_sequence` first; `stop_id` alone can be ambiguous for loops. Never guess a sequence from row number. Missing `start_date` must be resolved with schedule/descriptor context and ambiguity reported.

- Trip-level `CANCELED` removes the entire dated run from boarding options. A `SKIPPED` stop removes that call's boarding/alighting while through passengers may continue. Do not conflate it with a whole-trip cancellation.
- Preserve `NO_DATA` and clear prediction applicability as the specification requires. Missing updates are not necessarily evidence of on-time running. Delay propagation along later stops follows GTFS-RT rules and stops at explicit updates/NO_DATA boundaries.
- Arrival and departure estimates/delays are independent. Absolute event `time` takes precedence over `delay` when both are given. Preserve uncertainty and observation timestamps. Trip-level delays need propagation rather than blind duplication into every row.
- Assigned stop/platform changes are separate from scheduled stop identity. Use `assigned_stop_id` only if present and joinable; retain the raw ID when unresolved. Platform labels and RIV reported/extra statuses may require [stop-status enrichment](enrichment.md).
- New, duplicated, replacement, deleted, modified and unscheduled trips need their full descriptor semantics, sometimes a new call list. Preserve them in protobuf; surface unsupported/unmatched counts. Do not force them into a `tripIdx` that belongs to a different scheduled run.
- A new full snapshot replaces previous entity state. For a future differential reducer, entity deletion means remove that update from the retained feed state, not cancel the train. Retain enough source state for deletion, expiration and reconnects.

An updated planner must recompute effective times and sort accordingly. Scheduled connection pages only index scheduled departure times; delayed trips can cross page/region/date bounds. A request must account for the applicable overlay and extra trips before asserting completeness.

## Optional `delays-cancellations.arrow` (reserved)

This is a materialized convenience table, **not generated by the current collector**. Only publish after resolving GTFS-RT propagation and RIV observations against canonical entities and a pinned static release, using [field/source reconciliation](riv.md). It can contain effective RIV-sourced delays, with `sourceIri` identifying provenance. Exact fields, including IRI relationships, are in `schemas.mjs` under `delaysCancellations`:

| Fields | Arrow type | Nullable | Meaning |
| --- | --- | --- | --- |
| `tripIdx` | Int32 | no | Matched static trip |
| `serviceDate`, `stopSequence` | Uint32 | no | Dated call key; for trip scope, sequence is 0 and ignored |
| `scope` | Utf8 | no | `trip` or `stop`; disambiguates real sequence 0 |
| `scheduleRelationship` | Utf8 | no | Original GTFS-RT enum name in its trip/stop scope |
| `arrivalTime`, `departureTime` | Int64 | yes | Resolved effective UTC seconds |
| `arrivalDelay`, `departureDelay` | Int32 | yes | Signed effective delay seconds, including early running |
| `assignedStopIdx` | Int32 | yes | Resolved replacement boarding/alighting stop |
| `uncertainty` | Uint32 | yes | Conservative maximum event uncertainty seconds if collapsed; raw protobuf retains event-level details |
| `source` | Utf8 | no | Source namespace |
| `observedAt` | Int64 | no | Source measurement timestamp or feed timestamp if unavailable |

One current row per scoped key. Arrow snapshots replace previous rows as a whole; omitted rows clear old overrides. Null times/delays mean no resolved estimate, not zero. A trip cancellation overrides its stop rows. The overlay is not an archive of all update events and cannot fully express unindexed additional trips; keep raw protobuf discoverable and declare reconciliation coverage and unsupported counts. RIV partial arrival/departure cancellations remain separately represented in stop status. A future new-trip table should be designed before claiming normalized coverage for all GTFS-RT relationships.

ServiceAlerts are a different GTFS-RT payload; future collection should preserve them separately as `service-alerts.pb`, and optionally materialize the alert tables. VehiclePositions, including occupancy if actually provided, should likewise have their own canonical snapshot. Their existence in GTFS-RT does not prove SNCB currently supplies those fields.
